# VERIFICATION CHECKLIST

Verify every subsystem against these rules:

### Architecture

* All planned modules exist.
* No duplicate responsibilities.
* Single Responsibility Principle is respected.
* No circular dependencies.
* Modules communicate through defined APIs.

### Registries

Confirm these registries exist and are used:

* Settings Registry
* Token Registry
* Preset Registry
* Component Registry
* Template Registry
* Asset Registry
* Animation Registry
* Hook Registry
* Feature Registry

No hardcoded alternatives.

### Data Layer

* WordPress objects never reach components directly.
* Adapters normalize data.
* View Models prepare UI data.
* Renderers consume only normalized data.

### Rendering

* Components never output raw WooCommerce markup.
* Renderers own all HTML.
* Templates remain swappable.
* Frontend is independent of WordPress markup.

### Frontend

* HTML structure remains framework-agnostic.
* Bootstrap, vendor CSS, theme CSS, and animations are preserved.
* GSAP, Three.js, Lenis, Swiper, and Lottie load through the Asset Manager.
* No business logic is embedded in the frontend.

### Design System

* Settings Registry remains the single source of truth.
* Tokens resolve dynamically.
* Presets update tokens without duplicating settings.
* CSS variables are generated centrally.
* Theme DNA controls design behavior.

### Admin

* Admin pages use services and APIs rather than direct database access.
* Customizer and Theme Options update the Settings Registry.
* Design Studio interacts only with the Design System API.
* Demo Manager does not duplicate preset logic.

### Performance

* Assets load conditionally.
* Cache busting works.
* Lazy loading is implemented where appropriate.
* Critical CSS is supported.

### Extensibility

* New demos can be added without modifying the core.
* New components can register themselves.
* New presets can be added through providers.
* New plugins integrate through bridges.

### Safety

* No duplicate classes.
* No orphaned services.
* No dead code.
* No missing dependencies.
* No broken namespaces.
* No circular service registrations.
